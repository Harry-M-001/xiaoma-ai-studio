# 内置通用 Agent · 设计方案（2026-11-18）

> 用户指令：「我们先把通用 Agent 功能做上吧，然后通用 Agent 可以创建调用我们的自由画布。现在有好多通用 Agent 架构，你查 2026 年 10、11 月的稳定的新架构。我可以给你一个 KIE AI 的 API，你调用里面的模型测试用。」

这份文档先定**架构与边界**，通过后再动手。结论在最前面，依据在后面。

---

## 一、一句话结论

**自己写一个「单循环 harness」，工具层用我们自己的注册表，协议层只认 OpenAI 兼容的 `tools`，不引入任何 Agent 框架。** 画布不是「外部工具」，而是**一等公民工具组**（创建 / 读 / 改 / 连线 / 预估 / 执行）。第一版就做到「说一句话 → 画布上真的多出一张能跑的图」，而不是又一个聊天框。

三个关键决定：

1. **不引框架**（LangGraph / OpenAI Agents SDK / MAF / CrewAI 都不装）。理由见 §三：我们的硬约束（BYOK、本机、无 Docker、便携包）与它们的假设几乎全部冲突；而 2026 年真正值得抄的是**harness 的几条做法**，不是框架本身。
2. **工具不是全量挂载**。2026 年的主流共识是「上下文当预算」：工具描述按需加载（deferred tool loading），先给模型 8–12 个核心工具 + 一个「查更多工具」的元工具。
3. **写操作分三级、不可逆的一律要人点**，而且**「做完了」不算数**——判据是去库里查「工坊里真多了一个项目/画布/资产」。

## 二、2026 年 10–11 月的架构盘点（只列稳定、可借鉴的）

| # | 事实 | 时间/版本 | 对我们的意义 |
|---|---|---|---|
| 1 | **MCP 规范 `2026-07-28`** 落地：改成**无状态架构**，Streamable HTTP 修订（移除 GET 流等），官方称这是协议自发布以来最大的一次修订 | 2026-07-28（10–11 月仍在补 SDK） | 以后接「外部工具」按这个版本做；**本期不做 MCP 客户端**，但工具注册表的形状要能对上它（`name/description/inputSchema`） |
| 2 | **OpenAI Agents SDK 0.24.0**（Python，10-15 发布，要求 `openai>=3,<4`），TypeScript 同步 | 2026-10-15 | 它的核心就是「agent loop + handoff + guardrail」；我们可以只抄它的**运行轨迹（trace）与 guardrail 概念**，不装它 |
| 3 | **Microsoft Agent Framework 1.0**（2026-04 发布，AutoGen 进入维护模式、Semantic Kernel 10 月仍在发 1.45 但已指定它为继任者） | 2026-04 / 10 月更新 | 说明「多 Agent 编排」在退潮、**统一 harness** 在收敛；我们不需要多 Agent |
| 4 | **Harness engineering** 成为主流话题：上下文是**预算不是缓冲**；**按需加载工具 schema**；**结构化执行反馈**（命令/退出码/输出/错误，长输出中间截断）；**指针代替载荷**（把大结果写文件、只把路径给模型）；**证据可追溯** | 2026 下半年多篇工程文与论文 | 直接决定我们 harness 的四条实现口径（§四） |
| 5 | **Skills 的渐进披露**（名字+描述常驻、正文按需、附件最后）与「单循环往往比多 Agent 更快（实测约 2×）」 | Anthropic 2026 | 我们做「技能 = 一段 Markdown + 可选的工具白名单」，**多 Agent 不做** |

**结论**：2026 年没有出现「必须引入才能做 Agent」的新框架；出现的是**一套被反复验证的 harness 做法**。我们照做法做，代码量反而更小、可控。

## 三、为什么不引框架（约束对照）

| 约束（本项目已守很久） | LangGraph / CrewAI / Agents SDK / MAF 的假设 |
|---|---|
| 用户自填 Base URL + Key（BYOK），可能是 7B 本地模型 | 多数默认绑定自家或某几家的 SDK、需要特定 SDK 版本（如 `openai>=3`） |
| 本机可离线、无 Docker、Windows 便携包 | Python 依赖树大，进便携包要涨几十 MB |
| 素材不出门、调用记录要能审计 | 云端 trace/托管面板是它们的默认路径 |
| 已有 19 个 router / 118 个接口、自己的注册表 | 框架自带一套工具/状态抽象，等于第二套事实源，必然漂移 |

**这不是「框架不好」，而是「这套产品的约束与它们的默认假设相反」。** 与 9 月的调研结论一致（`docs/agent-research.md`：借约定、不借框架）。

## 四、我们的 harness：六个组件

```
用户输入
  → [1] 会话上下文装配（系统提示词 + 技能元数据 + 核心工具 + 最近 N 步）
  → [2] 模型回合（OpenAI 兼容 /chat/completions，tools）
      ├─ 文本 → 流式回给界面
      └─ tool_calls → [3] 工具网关（校验参数 → 权限分级 → 执行 → 结构化结果）
                        → [4] 落库（步骤/参数/结果/耗时/花费）
                        → 回到 [2]（有上限）
  → [5] 收尾校验（写操作要有证据）
  → [6] 界面：时间线 + 可回放 + 可中止
```

| 组件 | 第一版怎么做 | 明确不做什么 |
|---|---|---|
| [1] 上下文装配 | 系统提示词**现生成**（照 `canvas_agent` 那条口径：节点/参数/风格卡从注册表现取）；工具按「核心 10 个」挂载 | 不做向量记忆、不做自动摘要 |
| [2] 模型回合 | 走现有 provider 适配器的 OpenAI 兼容通道（`tools` 字段）；模型不支持工具调用 → 降级成「结构化建议 + 可点卡片」 | 不接 Responses API、不做多模型路由 |
| [3] 工具网关 | 每个工具声明 `tier: read / write / irreversible`、`schema`、`impl`；参数用 JSON Schema 校验；执行结果统一成 `{ok, data?, error?, hint?}` | 不给模型直接 SQL/HTTP |
| [4] 落库 | 新表 `agent_sessions` / `agent_steps`（参数、结果摘要、耗时、token、确认状态） | 不存全量上下文（只存可回放的步骤） |
| [5] 证据校验 | 写操作返回**工坊里的 id**，收尾时按 id 去库里查一遍；查不到就说失败并说原因 | 不信模型自述 |
| [6] 界面 | 左侧会话列表 + 中间时间线（每步可展开参数/结果）+ 右侧「产物/画布」；中止按钮 | 不做多 Agent 面板 |

**工具分层与确认**（沿用路线图 `#47` 已定的口径）：

| 级别 | 例子 | 谁决定 |
|---|---|---|
| 只读 | 列项目、读画布、读资产、查任务、预估成本、列模型/引擎 | Agent 自己决定 |
| 可撤销 | 建草稿画布、加/改节点、连线、改提示词 | Agent 自己做，界面标「可撤销」，提供一键回滚（利用画布快照） |
| 不可逆 | 派任务（花钱）、删项目/资产、执行整图 | **人点确认**；弹窗必须给出「几个任务 / 至少几次调用 / 哪些节点会重做」（复用 `preview_graph`） |

## 五、画布工具（这次的重点）

画布是我们的差异化：**别的 Agent 调不到创作资产**。第一版工具清单（名字即模型看到的函数名）：

### 5.1 只读（5 个）

| 工具 | 做什么 | 复用 |
|---|---|---|
| `list_projects` | 列出自由画布（id / 名称 / 更新时间 / 节点数） | `GET /api/projects` |
| `get_canvas` | 读一张画布的完整文档（节点、边、参数） | `GET /api/canvas/{id}` |
| `summarize_canvas` | 把画布压成「每节点一行」的摘要（指针代替载荷） | 新写，纯函数 |
| `preview_canvas` | 只算不跑：会执行几个节点、至少几次调用、哪些会重做 | `GET /api/canvas/{id}/preview` |
| `lint_canvas` | 分镜体检（零成本） | `GET /api/canvas/{id}/lint` |

### 5.2 写（4 个，可撤销）

| 工具 | 做什么 | 注意 |
|---|---|---|
| `create_project` | 建一个自由画布项目（可指定名字） | 幂等：同名不重复建，返回已有 id 并说明 |
| `draft_canvas` | **一句话 → 画布草稿**（复用 `canvas_agent` 的 JSON 拓扑 + 布局 + 宽容修复），**只回草稿、不落定** | 与画布页的「Agent 搭画布」共用同一份实现，不许抄第二套 |
| `apply_canvas_draft` | 把草稿落定到项目（覆盖/新建节点），返回画布 id 与节点数 | 落定前自动存一份快照，可一键回滚 |
| `update_node` | 改单个节点的提示词/参数 | 参数白名单来自 `NODE_SCHEMAS` |

### 5.3 不可逆（2 个，必须人点）

| 工具 | 做什么 | 确认弹窗要显示 |
|---|---|---|
| `run_canvas` | 执行整图（或指定节点） | 会派几个任务、至少几次调用、哪些节点已有产物会重做 |
| `run_node` | 执行单个节点 | 同上，单节点 |

> 产物不单独建工具：跑完的画布产物会出现在资产库，用 `list_assets` / `get_asset` 读即可（这两个归在只读核心工具里）。

### 5.4 为什么「创建 + 调用」要拆成 5+4+2

因为**模型最容易做错的就是「一步到位」**：让它直接 `create_and_run`，它会在参数没对齐时也把任务派出去（花钱且不可逆）。拆开之后，**建草稿不花钱、跑要人点**，每一步都看得见。

## 六、KIE AI 接入（测试用）

已核（2026-11-18）：KIE 是**聚合 API**，一个 Bearer Key 覆盖图像/视频/音频/聊天；**图像、视频、音乐是异步任务**（`create task` → `taskId` → `GET /api/v1/jobs/recordInfo` 或 webhook），**聊天模型是同步**；错误可能以 HTTP 200 + body 里的 `code` 返回（比如 401/429）；生成文件**保留 14 天**。

两种接法，按 Chat 模型的文档落地：

| 用途 | 接法 | 备注 |
|---|---|---|
| **Agent 的大脑（聊天 + 工具调用）** | 优先走它的 OpenAI 兼容 `/chat/completions`（若能对上我们的适配器），否则加一个 KIE 适配器 | **必须验证 `tools` 是否原样支持**；不支持就退到「结构化建议」那一档，并如实写在界面上 |
| **生图 / 生视频（测试画布的产物）** | 异步任务适配器（与现有可灵/即梦那类 `taskId` 轮询同形） | 它是**按次计费**的，测试时只跑最便宜的那几档 |

**现在缺的东西**：`docs/KIE.md` 里目前只有一行占位 `YOUR_KIE_API_KEY`。需要你把真 Key 放进那个文件（或直接发我）；我拿到后先用**一次最小请求**验证：① 鉴权；② chat 是否支持 `tools`；③ 流式与用量字段；④ 一个最便宜的媒体任务能否跑通。**验证结果决定 M1 用哪条通道，不猜。**

## 十一、实施记录（2026-11-18，M1–M3 已落地）

按用户 2026-11-18 的选择：**M1+M2+M3 一起做**，入口按「**会话 ↔ 画布绑定**」（暂不做「项目 = 本机文件夹」）。

### 11.1 落地了什么

| 组件 | 落点 | 说明 |
|---|---|---|
| 模型通道 | `providers/base.chat_once` + `openai_compat` 实现 | 非流式 + `tools`；其它适配器默认**拒绝**（不支持就明说），Agent 据此给出「换模型」的指路 |
| 数据 | `agent_projects` / `agent_sessions` / `agent_steps` + 迁移 `0018` / `0019` | 三层：**项目 → 任务（会话）→ 步骤**；项目挂一张自由画布，任务继承；旧会话留空进「未归档」 |
| 工具层 | `services/agent_tools.py`（24 个） | 只读 16 / 可撤销 6 / 不可逆 2；参数白名单来自 `NODE_SCHEMAS` 与 `canvas_agent._agent_params` |
| 技能 | `app/skills/*.md` + `services/agent_skills.py` | 三层只取两层：`name+description` 常驻提示词、正文由 `load_skill` 按需取（附件层不做） |
| 循环 | `services/agent_runner.py` | 8 轮上限；不可逆调用先算代价再停；历史由步骤重建（可跨请求续跑） |
| 接口 | `routers/agent.py` | meta / sessions CRUD / messages / confirm |
| 界面 | `pages/AgentPage.tsx` | 左：项目 → 任务两级；中：时间线（工具步骤可展开）+ 确认卡；底部输入；能力清单 |

**项目层的口径（2026-11-18 用户要求）**：「要有项目可以建任务，把不同项目任务的上下文分开」。所以项目不是文件夹（文件夹是 `#61/#62`），而是**上下文容器**：一个项目挂一张画布、下面开若干任务；项目名与说明会写进系统提示词，模型能知道自己属于哪个项目、也能用 `list_agent_projects` / `create_agent_project` 读写这一层。**删项目不删任务**（任务退回「未归档」）——用户想删的通常只是归类。

### 11.2 真机验证过的事（DeepSeek `deepseek-chat`）

1. 列画布：调 `list_projects`，回答里的 id / 名称 / 节点数与库里一致。
2. 建画布 + 草稿：`create_project` → `draft_canvas`（内部再调一次模型）→ 4 节点 3 连线。
3. 落定：`apply_canvas_draft` 写入成功，画布真有 4 节点；形状与前端保存一致（`type` 是真实节点类型）。
4. 预估：`preview_canvas` 报 3 次调用（纯读，不花钱）。
5. 确认门：`run_canvas` 不执行、只生成待确认步骤，带「3 次调用 / 1 个待执行 / 0 个重做」。
6. 拒绝：点取消后模型如实回「没有执行、没有花钱」，并给出替代方案。
7. **项目隔离**：项目 A 绑画布 13、项目 B 不绑；在 B 里问「你知道另一个项目叫什么吗」，它只从 `list_agent_projects` 看到项目名，**看不到 A 的任务内容**，并如实说明这一点。
8. 删项目：任务仍在，`agentProjectId` 变 `null`（进「未归档」）。
9. **技能渐进披露**：说「做一条 30 秒短片，先别动手」，它先调 `load_skill("short-video")`，再按技能里的次序（草稿 → 体检 → 报成本 → 等人确认）回答，且明确说「不会自己点确认」。

### 11.3 明确没做（下一期）

- **M4 剩余**：MCP 客户端（按 `2026-07-28`）、更多工具（资产写入 / 提示词写入 / 引擎安装）。
- **文件与命令执行**（路线图 `#61/#62`）：这一轮不碰，危险且与本期的「调画布」无关。**Agent 项目目前不是本机文件夹**，只是上下文容器；文件夹形态要等文件工具那一期。
- **多 Agent / 子 Agent**：2026 年的实践反而在收回主循环，不做。
- **KIE 已接通**（2026-11-18）：`docs/KIE.md` 的 Key 已实测。**聊天**走 `/<模型>/v1/chat/completions`（Base URL 带模型段，一个聊天模型一条服务），**支持 `tools`**；**图片/视频**走 `providers/kie.py` 的异步任务适配器（`createTask → recordInfo → 下载`）：文生图、**参考图编辑**（本地图先上传成 URL）、Kling **首帧生视频 / 文生视频**，均已真跑通过。模型按命名分流（`*-edit` / `*-image-to-video` / `*-text-to-video`），**认不出就报错不猜**。两个坑：① 带 `tool_calls` 的 assistant 消息 content 不能为空；② 业务错误是 HTTP 200 + `{"code":…}`，必须当失败处理。

### 11.4 已知边界
